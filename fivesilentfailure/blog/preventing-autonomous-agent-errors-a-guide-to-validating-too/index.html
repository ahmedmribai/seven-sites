The Importance of Pre-Execution Validation

Validating tool outputs before they trigger irreversible actions turns a potential cascade of waste into a controllable checkpoint. When an autonomous agent mistakenly calls a cloud‑scale function — say, spinning up a large EC2 instance to process a non‑existent inventory update — the compute runs until the agent notices the mistake or a monitoring alarm fires. Catching the bad call at the validation layer stops the instance from launching, saving the hourly on‑demand rate (for a t3.large in us‑east‑1, about $0.083 per hour) and the associated data‑transfer charges that would otherwise accrue for every minute the resource lives. In a typical ops shift, a single missed validation can therefore avoid several dollars of unnecessary spend, and when the error repeats across dozens of agents the savings scale linearly.

The same principle applies to financial tooling. A Stripe refund that exceeds the original payment incurs the standard processing fee (2.9 % + $0.30) on the erroneous amount and opens the door to chargeback disputes or regulatory scrutiny. By enforcing a rule such as “refund amount ≤ original payment” before the API request is sent, ToolGuard blocks the over‑refund, preserving the fee revenue and keeping the transaction within PCI‑DSS limits. For a $200 mistaken refund, the avoided fee is $6.10; preventing just one such mistake each week removes roughly $300 of avoidable cost per year.

Beyond direct monetary impact, pre‑execution validation cuts debugging time. When an agent’s action fails silently — updating inventory with a wrong SKU, for example — the resulting discrepancy must be traced through logs, reconciled with warehouse systems, and manually corrected, often consuming hours of analyst effort. By confirming that the SKU exists in the product database before the update is issued, the erroneous write never occurs, eliminating the need for post‑mortem investigation and keeping the inventory record accurate from the start. In environments where agents run thousands of tool calls per day, this reduction in rework translates into measurable labor savings and faster incident response.

How ToolGuard Works

ToolGuard is a lightweight Python library that sits between an autonomous agent and the tools it invokes, intercepting every call before it reaches the external service and running a series of checks that decide whether the action should proceed. Its core feature is pre‑execution validation: each tool call is evaluated against a set of rules that can be simple Boolean checks — such as confirming that an order ID exists in a relational database — or more nuanced LLM‑driven sanity checks that ask whether the proposed response aligns with the agent’s stated intent. If any rule fails, the call is blocked and an informative exception is returned, preventing irreversible changes like erroneous API charges or corrupt database writes.

Getting started requires only two steps. First, install the package from PyPI with `pip install toolguard`. Then, in the agent’s code, wrap the tool invocation with the provided decorator or context manager. For example, a typical Stripe charge call becomes:

```python

from toolguard import validate

@validate

def create_charge(amount, currency, source):

return stripe.Charge.create(amount=amount, currency=currency, source=source)

```

When the decorator is applied, ToolGuard automatically loads its default rule set, which includes validators for common services such as Stripe, Shopify, AWS EC2, and PostgreSQL. These defaults check for obvious mistakes — like attempting to charge a negative amount, creating an EC2 instance of a disallowed type, or updating a product quantity below zero.

To tailor the library to a specific domain, users supply a YAML or JSON configuration file that defines additional rules. A cloud‑ops team troubled by an inexplicable spike in their bill might add a rule that any `ec2:RunInstances` call must verify that the requested instance count does not exceed the current running count by more than 10 % and that the instance type is limited to the family approved for cost‑saving workloads. Similarly, an e‑commerce team facing inventory mismatches could specify that inventory adjustment calls must ensure the new quantity equals the prior quantity plus any inbound shipment recorded in the procurement system, rejecting any deviation.

Because ToolGuard focuses solely on validating tool outputs, it adds minimal overhead — typically a few milliseconds per call — while catching the class of errors that lead to inflated cloud bills, corrupted data, and agents that appear to obey instructions yet fail to address the underlying problem. The library can be extended later with logging and auditing features, but its initial value lies in preventing costly, irreversible mistakes before they happen.

Using ToolGuard’s LLM‑powered sanity check — “Does the refund amount match the original transaction amount within tolerance?” — the team caught the mismatch before the Stripe API call was made. The guard flagged the anomaly, prompted a human review, and the refund was corrected, averting a potential violation of card‑network rules and the associated fees.

These examples show how a few lines of validation code, backed by ToolGuard’s default and customizable rules, stop costly tool‑output errors at the source, aligning agent behavior with the intended business outcome and keeping both costs and compliance under control.

To get started with ToolGuard, run `pip install toolguard>=0.4.0` in your environment. The library adds a single decorator `@toolguard.validate` that intercepts any function returning a tool‑call result. For a typical Stripe charge, wrap the call like this:

```python

import stripe

from toolguard import validate

@toolguard.validate

def create_charge(amount, currency, source):

return stripe.Charge.create(

amount=amount,

currency=currency,

source=source,

description="Order payment"

)

```

ToolGuard ships with pre‑built validators for Stripe, Shopify, and AWS SDK calls; they fire automatically when the decorated function returns a response object. If the charge amount exceeds a preset limit, the validator raises `ToolGuardValidationError` and the transaction is aborted before it reaches Stripe’s API.

To add domain‑specific rules, create a `toolguard.yaml` file alongside your code:

```yaml

rules:

- id: refund_limit

match: tool == "stripe.Refund.create"

condition: refund.amount <= original_payment.amount

message: "Refund cannot exceed original payment"

```

Reload the config with `toolguard.load_config("toolguard.yaml")`.

If you see unexpected cloud spend, enable debug mode: `toolguard.set_debug(True)`. This prints each intercepted call, the validator that ran, and whether it passed or failed, letting you trace why an inventory update or extra API request occurred. Common hiccups include mismatched library versions (ensure Stripe ≥ 5.0.0) and silent failures caused by importing ToolGuard after the tool module—place the import at the top of the file to guarantee the decorator is applied before the function definition.
