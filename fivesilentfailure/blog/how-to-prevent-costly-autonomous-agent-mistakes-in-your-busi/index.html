How ToolGuard Works in Practice

Here’s how ToolGuard intercepts a costly mistake in real time. Imagine an e-commerce agent tasked with issuing refunds via Stripe. Without validation, the agent might misinterpret a customer request and refund $1,000 instead of $100 due to a decimal error—a $900 loss that’s irreversible once processed. With ToolGuard, the refund call is wrapped in a pre-execution check:

1. **Intercept**: The agent prepares a Stripe API call to refund `amount=1000` (in cents). ToolGuard intercepts this call before it executes.

2. **Validate**: A prebuilt rule fires: `refund_amount <= original_payment_amount`. ToolGuard fetches the original transaction ($100) and flags the discrepancy.

3. **Block or Alert**: The invalid call is blocked, and the ops team receives an alert: "Refund $1,000 rejected: exceeds original payment of $100. Suggested action: Verify decimal placement."

For cloud cost spikes, ToolGuard can enforce rules like `max_ec2_instances=5` or `approval_required_for_aws_batch_jobs_over_1hr`. If an agent attempts to spin up 50 instances, the call is halted until manually reviewed. Similarly, inventory mismatches are caught by cross-checking agent-generated purchase orders against warehouse databases—e.g., "Agent ordered 500 units of SKU-X, but warehouse capacity is 200. Override required."

Custom rules are added via a YAML config. For example:

```yaml

- tool: stripe.refund

rule: "refund.amount <= query('SELECT amount FROM payments WHERE id = ?', refund.payment_id)"

on_fail: "reject"

```

This ensures every refund is validated against the actual payment record. The entire process adds <50ms latency—far cheaper than reconciling financial or logistical errors after the fact.

**Key takeaway**: ToolGuard doesn’t just detect failures—it prevents them by injecting hard stops before faulty executions commit. The rules are simple, but the savings are real: one blocked $900 refund pays for months of runtime.

Similarly, to tackle inventory mismanagement, you might configure ToolGuard to validate that any database write altering stock levels includes a valid SKU and matches the expected transaction type (e.g., restock vs. sale). These rules act as guardrails, ensuring that agents operate within your business’s operational boundaries.

Customizing ToolGuard is straightforward. After installing the library with `pip install toolguard`, you define your rules in a YAML or JSON file. For instance, to prevent agents from issuing refunds exceeding the original payment amount, you could write a rule like this in YAML:

```yaml

rules:

- name: validate_refund_amount

tool: stripe.refund

condition: refund_amount <= original_payment_amount

error_message: "Refund amount exceeds original payment."

```

These configurations are loaded into ToolGuard with a single line of code, seamlessly integrating into your existing workflows.
